# Postmortem контролируемого отказа демостенда

Тип: заранее ограниченное локальное упражнение. Не production и не отказ у покупателя. Отдельный процесс ShopKZ с временной SQLite остановлен и запущен снова. Основание анализа: results/incident.json. Обвинения людей не используются: анализируются условия и защитные механизмы.

## Влияние

Пять из одиннадцати контрольных проб были неуспешны. Наблюдаемый промежуток от первой ошибки до первого успешного ответа 2.853 с. Время до подтверждения трех успешных проб длиннее и сохранено в events. Период опроса 0.5 с ограничивает точность. Реальные клиенты и production данные не затронуты. Потеря заказа не заявлялась и в этом упражнении не измерялась.

## Факторы

Непосредственный триггер — намеренная остановка демопроцесса. Самостоятельного supervisor/restart в локальном запуске не было, поэтому требовалось действие оператора. Контроль HTTP был отдельным Python probe; Uptime Kuma еще не поднят из-за отсутствия Docker. Покрытие приложением сценариев checkout не защищает от отсутствия самого процесса. Процентный вклад факторов определить по одному упражнению нельзя.

## Что сработало

Изоляция базы ограничила влияние. Быстрый HTTP probe зафиксировал DOWN и UP, лог содержит время каждого наблюдения. Запуск той же версии с той же временной базой восстановил каталог. Три последовательных успеха снизили вероятность принять одиночный ответ за устойчивое восстановление.

## Что улучшить

Автоматическое восстановление пока не проверено. Контейнерный мониторинг и учебный rollback требуют отдельной машины с Docker и реального журнала выполнения. Внешняя приемка остается отдельным событием.

## Проверка корректирующих действий 03.11.2026

GitHub Actions run 41639836731, job monitoring: success. Kuma в Docker зарегистрировал UP/DOWN/UP (HTTP timeout 3 с, интервал 20 с, retries=0). Автоматический перезапуск тренировочного приложения подтверждён RestartCount=1 и тремя последовательными HTTP 200 за 4,561 с наблюдения. Это не production MTTR.
